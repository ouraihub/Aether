# AI 工程规范：可维护的跨语言项目

> 版本：1.0  
> 适用：由大模型参与设计、编码、重构、测试和维护的项目  
> 目标：让大模型输出可理解、可验证、可回滚、可长期维护的代码。

## 1. 适用范围与优先级

本规范约束生产代码、测试、脚本、文档、接口、错误、日志和数据库变更。

规则优先级：

1. 安全、数据完整性和法律要求
2. 公共协议、数据库迁移和对外 API 合同
3. 本规范
4. 项目局部规范
5. 大模型默认偏好

项目可以扩展本规范，但不得降低安全、错误处理、测试和验证要求。项目局部规则必须写明覆盖的章节、原因、范围和失效条件。

## 2. 大模型工作合同

大模型在修改代码前 MUST：

1. 读取项目根级协作规则和本规范。
2. 确认目标模块、公开入口、调用方、测试和构建命令。
3. 搜索将要修改的函数、类型、字段、错误码和命令的全部调用方。
4. 复用现有接口、类型、工具和约定，不建立平行实现。
5. 先说明问题、根因、影响范围和验证方案，再修改代码。
6. 一次变更只服务一个可描述的行为目标。

大模型 MUST NOT：

- 猜测未读取的 API、文件或项目约定。
- 为了通过检查删除、跳过、放宽或屏蔽测试。
- 用兼容别名、空实现、默认回退或吞错掩盖契约冲突。
- 顺手升级依赖、重命名公共字段、改数据库格式或扩大权限。
- 把格式化、重构和功能变更混在一个不可审查的 diff 中。
- 把源码字符串存在、函数被调用或“不抛异常”作为行为证明。

交付 MUST 包含：变更文件、行为说明、验证命令、实际结果和未验证项。未观察到的结果不得写成已通过。

## 3. 架构原则

### 3.1 面向接口

接口只出现在真实边界：

- 宿主与共享能力
- 应用服务与存储
- 执行引擎与工具
- UI 与后端
- 网络、时钟、文件、进程和外部服务
- 测试需要替换的外部资源

接口由使用方定义。只有一个实现且不跨边界的内部函数、模块或结构体 SHOULD NOT 包装成 trait、interface、factory 或 adapter。

判断顺序：

```text
跨边界或需要替换？定义接口。
仅为纯函数或内部调用？直接使用函数。
只有一个实现且没有替换需求？不要增加抽象。
```

实现 MUST 通过构造参数或组合根注入。禁止全局单例、隐式注册顺序、运行时扫描或插件顺序探测依赖。

### 3.2 面向对象

```text
状态 + 行为 + 不变量 → 对象
纯输入输出变换       → 函数
跨边界可替换资源     → 接口
```

- 字段默认私有。
- 构造函数和写方法负责维护不变量。
- 对外暴露意图明确的操作，不暴露可任意修改的集合或锁。
- 组合优于继承。
- 不为每个 DTO、工具函数或模块机械创建 class。
- 生命周期、取消、关闭和资源释放必须由明确所有者管理。

### 3.3 模块化

每个模块 MUST 有一个清晰职责、一个公开入口和明确的资源所有者。

- 公开入口只导出稳定合同。
- 内部实现默认私有。
- 依赖方向单向；禁止循环依赖。
- 一个状态机只有一个权威实现。
- 一个错误合同只有一个权威定义。
- 一个 DTO 只有一个生成或维护来源。
- 事务和安全不变量必须由一个协调入口维护，不能交给调用方拼接。

文件大小是审查信号，不是设计目标：生产文件超过 300 行 SHOULD 评审，超过 500 行 MUST 说明职责边界并优先按职责拆分。测试、生成文件、fixture、许可证、迁移 SQL、长资源字符串和第三方代码不机械套用该阈值。

### 3.4 组件化

组件必须有稳定输入、明确输出和单一职责。

展示组件：

- 只接收 props 或参数。
- 只通过回调报告用户意图。
- 不直接访问后端、数据库、全局单例或平台 API。

容器组件：

- 负责依赖注入和流程状态。
- 调用领域接口，不实现后端业务规则。
- 不复制另一套状态机或事务流程。

共享组件 MUST 复用现有合同和设计系统。不存在第二套 Button、Dialog、Port、DTO 或错误转换。

## 4. 日志规范

日志 MUST 是结构化事件：

```text
<module>.<object>.<action>
```

示例：

```text
providers.probe.failed
chat.run.finished
mcp.server.forbidden
```

字段 MUST：

- 使用稳定、扁平、可检索的字段名。
- 记录 ID、状态、错误码、计数、耗时和大小。
- 同一事件使用稳定字段集合。

日志 MUST NOT 包含：

- 密钥、token、密码、Authorization、Cookie。
- 带凭据的 URL 或请求头。
- 用户输入正文、模型输出、技能正文和工具参数原文。
- SQL、文件路径或底层异常中的敏感细节。

级别：

| 级别 | 用途 |
| --- | --- |
| `error` | 需要人工处理、可能丢数据或程序错误 |
| `warn` | 降级、拒绝或已自动恢复 |
| `info` | 生命周期和关键业务节点 |
| `debug` | 默认关闭的诊断细节 |

一个错误 MUST 只在最终处理层记录一次。循环中 MUST 汇总记录，不逐项写日志。核心库只发出日志事件或使用注入 logger，不自行安装全局订阅器。

## 5. 异常与错误规范

错误分为两类：

1. 预期错误：输入非法、未配置、未授权、冲突、限流、超时、上游失败和取消。
2. 程序错误：不变量破坏、未知状态和 bug。

预期错误 MUST 有稳定错误码。调用方 MUST 按错误码或类型分支，NEVER 按错误文案、字符串包含或正则判断错误类别。

程序错误 MUST：

- 冒泡到明确边界。
- 生成可关联的错误 ID。
- 对用户和外部调用方返回脱敏通用错误。
- 在最终边界记录一次必要诊断信息。

异常处理只能做三件事：

- 按明确错误码处理并恢复。
- 增加上下文后重新抛出。
- 在最终边界记录并通知调用方。

禁止：

- 空 `catch`、空 `Err` 分支和静默忽略 Promise。
- 用默认值掩盖非法输入。
- 捕获后继续使用可能不完整的数据。
- 在取消后伪造成功。
- 对可能产生外部副作用但结果未知的操作自动重放。

跨边界的错误必须转换为该边界的公共错误类型，不能泄漏底层路径、SQL、凭据或上游原文。

## 6. TypeScript / JavaScript

MUST：

- 开启 `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`noUnusedLocals` 和 `noUnusedParameters`。
- 使用 `unknown` 后收窄，禁止用 `any` 绕过类型系统。
- 对象合同使用 `interface`；联合、字面量和工具类型使用 `type`。
- 使用标签联合表达状态机，并穷尽处理分支。
- 使用 `import type`。
- Promise 必须 `await` 或显式 `void`，并说明后台任务的所有权和错误处理。
- 可取消操作接收 `AbortSignal`。
- 公共 DTO 只来自唯一合同来源，不在 UI 或后端复制。
- 外部输入先运行时校验，再进入内部类型。
- 不使用非空断言、隐式全局状态或文案判断错误。

推荐工具：TypeScript、ESLint、Prettier、测试框架和依赖方向检查。

格式目标：100 列。Prettier 的 `printWidth` 是排版目标，不是硬上限；需要硬限制时使用独立检查并保留 URL、不可拆分字符串等明确例外。

## 7. Svelte 5

MUST：

- 只使用 runes：`$state`、`$state.raw`、`$derived`、`$effect`、`$props`、`$bindable`。
- 状态和异步流程放在 `*.svelte.ts` 状态类中。
- `$effect` 只用于订阅和 DOM 同步；有资源就返回清理函数。
- 能使用 `$derived` 时不使用 `$effect`。
- 异步结果使用 `AbortSignal` 或 generation 丢弃过期结果。
- 依赖注入使用 context，不使用模块级单例。
- 展示组件只使用 props 和回调；容器组件才访问 context 和端口。
- 使用原生可访问控件；图标按钮必须有 `aria-label`。
- 禁止 `export let`、`$:`、`on:event`、`<slot>`、`createEventDispatcher`、`svelte/store` 和未经清洗的 `{@html}`。
- 关闭弹窗必须清理遮罩、焦点和交互状态。

组件测试 MUST 使用用户可观察行为和可访问性断言，不测试复制实现、转发调用或源码字符串。

## 8. Rust

MUST：

- 使用 `rustfmt`、稳定工具链和项目锁定的 edition。
- 启用 workspace lints 和 `clippy -D warnings`。
- 核心 crate 不依赖 UI 或平台接入层。
- 优先借用；只有需要所有权时才传 `String`、`Vec` 或复制数据。
- 使用 enum 表达状态机，match 分支尽量穷尽，禁止无理由的 `_` 兜底。
- trait 只用于真实边界或测试替换。
- SQL 使用参数绑定；相关写入放在同一事务；迁移只追加。
- 使用 `Result` 和 `?` 传播错误。
- 生产代码禁止无理由 `unwrap`、`expect`、`panic!`、`todo!`、`unimplemented!` 和 `dbg!`。
- `unsafe` 必须有最小范围、理由和 `SAFETY` 注释。
- 公开项写文档；公开错误返回写 `# Errors`。
- 敏感类型手写 `Debug`，不把明文凭据序列化。

测试组织：

- 单元测试放在 `src`，用于访问私有实现。
- 集成测试放在 crate 的 `tests/`，只使用公开 API。
- `tests/common/mod.rs` 用于共享集成测试辅助代码；不要使用无测试函数的 `tests/common.rs`。
- 测试按职责拆分，不为满足行数机械复制 fixture。

## 9. Python

MUST：

- 使用 4 空格缩进，不混用 tab。
- 使用 Black 或 Ruff formatter，项目固定一个工具链。
- 使用 Ruff lint；类型要求明确时使用 mypy 或 pyright，项目固定一个。
- 函数和类保持单一职责；纯变换与 I/O 分离。
- 不使用可变默认参数。
- 外部输入先校验，文件和网络资源使用上下文管理器。
- 只捕获能处理的异常；禁止裸 `except` 和静默吞错。
- 不在库代码中使用无结构 `print` 作为日志。
- 测试放在 `tests/`，测试行为、边界和错误，不测试实现细节。
- 代码行宽目标采用 formatter 默认值；本项目默认 Ruff/Black 88，注释和 docstring 遵循项目 formatter。

## 10. 测试规范

测试优先级：

1. 公共合同和安全边界
2. 状态转换和不变量
3. 错误码、取消、超时和副作用未知
4. 端到端公共行为
5. 纯函数边界

永久测试 MUST 捕获真实消费者可观察的失败。禁止只测试：

- 函数被调用。
- 参数被原样转发。
- 类型或文件存在。
- 源码包含某个字符串。
- “没有抛异常”。
- 生成数组非空或长度增加。

修 bug MUST 保留回归测试。网络测试使用本地可控服务；不得访问开发者真实数据、真实凭据或不受控外网。

测试文件拆分按职责：

```text
单元测试：src/<module>_tests.rs 或 src/<module>/tests.rs
集成测试：tests/search.rs、tests/fetch.rs、tests/security.rs
共享夹具：tests/common/mod.rs
```

## 11. 规模、格式和 diff

默认目标：

| 内容 | 目标 |
| --- | ---: |
| Rust | 100 列 |
| TypeScript / JavaScript / Svelte / Node | 100 列 |
| Python | formatter 默认，通常 88 列 |
| C# / F# / VB.NET | 120 列 |
| 生产实现文件 | 500 行以内 |
| 复杂函数 | 通常不超过 60 行 |

例外必须是有名字、有原因、可审查的例外。生成代码、测试 fixture、许可证、迁移 SQL、长 URL、HTML/CSS 资源和第三方代码不应被机械重排。

格式迁移和功能变更 MUST 分开。大模型修改已有代码时 SHOULD 只格式化触及的文件；全仓格式化必须单独提交。

## 12. 大模型变更流程

### 修改前

- 读取本规范、项目规则和目标模块入口。
- 搜索全部调用方和测试。
- 确认是否已有接口、类型、错误、日志和 helper。
- 写出最小变更方案和验证命令。

### 修改中

- 只实现用户要求的行为。
- 保持公开合同和错误语义稳定，除非用户明确要求变更。
- 不新增不必要抽象、依赖、线程、缓存、重试或配置项。
- 资源、锁、任务和取消必须有明确所有者。
- 每个复杂逻辑保留一个最小行为测试。

### 修改后

- 先运行格式和静态检查。
- 再运行类型检查和定向测试。
- 再运行受影响模块的集成测试。
- 最后运行项目 CI。
- 检查 diff 是否只包含目标变更。
- 报告实际通过、失败、跳过和未验证项。

## 13. 例外申请

无法遵守规则时，必须在代码或项目规范中记录：

```text
规则：违反哪一条
范围：哪些文件或模块
原因：为什么不能采用默认方案
风险：可能造成什么维护或安全风险
替代措施：如何验证和限制风险
失效条件：什么时候必须移除例外
```

例外不能用于绕过安全、数据完整性、输入校验、错误处理或行为测试。

## 14. 项目采用方式

将本文件复制到公共基座或宿主项目的 `docs/AI工程规范.md`，并在根级 `AGENTS.md`、`CLAUDE.md` 或等效 AI 入口中加入：

```markdown
开始任何编码任务前，必须读取 docs/AI工程规范.md。
它约束架构边界、接口、模块、日志、错误、语言、测试和验证。
项目局部规则只能扩展它，不得降低安全、错误处理和验证要求。
```

项目还必须提供：

- 根目录验证命令。
- 语言 formatter 和 linter 配置。
- 测试命令及最小集成冒烟命令。
- 生成文件和第三方代码的明确边界。
- 项目特有的架构入口和公共合同位置。

公共组件项目应把稳定接口、DTO、错误码、事件和行为场景写进公共合同；宿主项目只添加业务策略、登录、资源授权和界面组合，不复制共享执行逻辑。
