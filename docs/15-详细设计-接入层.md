# 15 详细设计：接入层 tauri-plugin-aether

> 依赖：按 feature 依赖各核心 crate 与 aether-observability。**模块间组合只发生在这里。**
> 蓝本：AutoNote `desktop/src-tauri/src/commands/ai.rs`（Channel 流式、jobs 取消）、`desktop/src/lib/ipc/transport.ts`（前端调用与取消）。

## 1. Features

| feature | 依赖 crate | 注册的命令前缀 | 需要 |
| --- | --- | --- | --- |
| （始终） | aether-observability | `logs_*` | `LogHandle` |
| `providers` | aether-providers | `providers_*` | `providers::Store` |
| `chat` | aether-chat | `chat_*` | `chat` 需要 `providers`；可选 `ConversationStore` |
| `skills` | aether-skills | `skills_*` | `skills::Store` |
| `mcp-client` | aether-mcp-client | `mcp_client_*` | `mcp_client::Store` |
| `mcp-server` | aether-mcp-server | `mcp_server_*` | `McpServer` |

默认全关。未启用的 feature 不编译对应依赖、不注册命令、不声明权限。

## 2. Builder

```rust
pub struct Builder { /* host、logs、各 Option<实例> */ }
impl Builder {
    pub fn new(host: Arc<dyn KitHost>, logs: LogHandle) -> Self;
    #[cfg(feature = "providers")]  pub fn providers(self, s: aether_providers::Store) -> Self;
    #[cfg(feature = "chat")]       pub fn chat(self, cfg: ChatConfig, store: Option<Arc<dyn ConversationStore>>) -> Self;
    #[cfg(feature = "skills")]     pub fn skills(self, s: aether_skills::Store) -> Self;
    #[cfg(feature = "mcp-client")] pub fn mcp_client(self, s: aether_mcp_client::Store) -> Self;
    #[cfg(feature = "mcp-server")] pub fn mcp_server(self, s: aether_mcp_server::McpServer) -> Self;
    pub fn build<R: Runtime>(self) -> Result<TauriPlugin<R>, KitError>;
}
pub struct ChatConfig { pub budget: Budget /* Budget::default()，max_output/context_window 按模型已知值覆盖 */, pub approval_timeout: Duration /* 默认 5 分钟 */ }
```

`build()` 校验：

- 启用了某 feature 却没传实例 → `bad_request{reason:"missing_instance", field:"<feature>"}`。
- 传了 `chat` 却没传 `providers` → 同上，`field:"providers"`（先于其他缺失项检查）。
- 传了 `chat` 的 `store: None` → 无历史模式：`conversationId` 恒为 `null`、`regenerate` 报 `bad_request{reason:"no_conversation"}`，`aether:chat-history` 命令不分派（前端得到 `Command not found`）。
- 其余能力相互独立；没有注册顺序要求，不在运行时探测其他插件。

## 3. KitHost

定义见 00 §5.1。补充约定：

- 所有方法同步调用的（`select_model`、`system_prompt`、`context`、`tools`、`authorize`）在 `spawn_blocking` 中执行，宿主可以直接读自己的数据库。
- `HostTool { spec: ToolSpec }` 与 Chat 的 `ToolSpec` 同形（名称、描述、schema、`approval` 默认值）。
- `call_tool` 返回 `ToolOutput { text, payload }` 或 `ToolError { code, message, unknown: bool }`；`unknown=true` 表示副作用可能已发生。

```rust
pub struct RunRequest {
    pub purpose: String,                // 应用自定义，如 "chat"、"polish"；aether 不解释
    pub model: Option<ModelRef>,        // UI 显式选择
    pub skills: Vec<SkillRef>,
    pub context: Option<ContextRef>,    // { kind, id }，由应用定义
    pub input: String,
    pub conversation_id: Option<String>,
    pub scope: Option<String>,
    pub regenerate: bool,
    pub reply_to_id: Option<String>,
    pub retry_turn_id: Option<String>,
    pub translate_turn_id: Option<String>,
    pub target_language: Option<String>,
    pub language: String,
}
```

## 4. 一次运行的组装（`chat_run`）

1. 反序列化 `RunRequest`（`deny_unknown_fields`；`input` ≤ 100 000 字符；`skills` ≤ 20 项）。
2. `host.select_model(&req)` → `providers.resolve(&model)` → `Connection`。
3. `skills.snapshot(&req.skills)`（未启用 skills feature 且 `skills` 非空 → `unsupported`）。
4. `host.system_prompt`、`host.context`。
5. 工具目录：`host.tools(&req)` + `mcp_client.session().tools()`（转成 `ToolSpec`，`source=Mcp`）；**重名直接报错**（交给 Chat `validate`）。
6. 历史：有 store 则 `begin_turn` 并读取已完成的轮。
7. `runner.validate(&mut input)`。
8. 以上任一失败：命令返回 `Err(KitError)`（请求错误），不发任何事件，不写会话（`begin_turn` 前失败）或删除刚开始的轮。
9. 成功：登记run_id，返回 `{ runId, conversationId, turnId }`，tokio任务执行runner.run；retry/translation字段互斥、不与regenerate组合，写作由宿主拒绝；语言1–80字符，动作消息ID最多128字符；同会话归属与模型快照先校验。
10. 事件经 `Channel<RunEvent>` 发送；**发送失败（窗口关闭/面板卸载）→ 触发 cancel**。
11. 结束：先finish_turn持久化，再发送唯一end事件；写库失败不能发送成功。移除run_id并记脱敏运行日志。请求历史沿replyToId或持久selectedTurnId；候选重答保留来源model/input/父路径，显式换模型才覆盖来源。

合成的 `ToolExecutor`：`execute` 按 `source` 分派到 `host.call_tool` 或 `McpSession::call`；`authorize` 直接调用 `host.authorize(call, default)`。MCP 结果以原文交给 Chat，由 Chat 按 `ToolSource::Mcp` 做外部内容包装（12 §5；只此一层边界）。启用 mcp-server 且其正在运行时，把端口传给 `session(cancel, own_port)`（13 §9.2）。

`Approver`：发出 `approval_required` 后等待 `chat_approve(runId, callId, allow)`，或运行取消，或 `approval_timeout` 到期（视为拒绝）。

## 5. 命令与权限

权限按命令声明（`permissions/<command>.toml`），并提供按能力分组的集合；**启用 feature 不等于授权**，应用必须在 capability 中给具体窗口引用权限。

  命令权限与集合（`aether:<feature>`）由 `build.rs` 每次构建按已启用 feature 重新生成到 `permissions/autogenerated/`（不提交）；未启用的 feature 没有命令也没有权限标识。因此静态 capability 文件不能引用可能未启用的集合，宿主按自身 feature 在 `setup` 中 `add_capability`（见 `examples/assistant`）。`aether:logs` 始终生成，可直接写进静态 capability。
  未启用 feature 时前端调用得到 Tauri 的 ACL 拒绝：`aether.<command> not allowed. Command not found`。

| 命令 | 参数 | 返回 | 权限集 |
| --- | --- | --- | --- |
| `logs_tail` / `logs_get_level` / `logs_set_level` / `logs_ingest` / `logs_open_dir` | 见 10 文档 §10 | | `aether:logs` |
| `providers_list` / `_save` / `_delete` / `_model_options` | 见 11 文档 §3 | | `aether:providers` |
| `providers_probe` / `providers_cancel` | `{ jobId, target }` / `{ jobId }` | `ProbeResult` | `aether:providers` |
| `chat_run` | `{ request: RunRequest, onEvent: Channel<RunEvent> }` | `{ runId, conversationId \| null }` | `aether:chat` |
| `chat_cancel` | `{ runId }` | `{ ok: true }`（未知 id 也 ok） | `aether:chat` |
| `chat_approve`（CH4-3 注册） | `{ runId, callId, allow: boolean }` | `{ ok: true }` | `aether:chat` |
| `chat_conversations` | `{ scope: string \| null }` | `ConversationSummary[]`（最近 200 条） | `aether:chat-history` |
| `chat_conversation` / `chat_delete` | `{ id }` | `Conversation`（turn 只含 input、各轮助手文本合并为 `text`、状态、`errorCode`）/ `Ack` | `aether:chat-history` |
| `chat_rename` | `{ id, title }` | `ConversationSummary` | `aether:chat-history` |
| `chat_edit_turn` | `{ conversationId, turnId, text, expectedText }` | `Conversation` | `aether:chat-history` |
| `chat_remove_turn` / `chat_select_turn` / `chat_fork` | `{ conversationId, turnId }` | `Conversation` | `aether:chat-history` |
| `skills_list` / `_get` / `_preview` / `_install` / `_save` / `_duplicate` / `_reorder` / `_delete` | 见 14 文档 §6 | | `aether:skills` |
| `mcp_client_list` / `_save` / `_delete` / `_refresh` / `_set_tool_approval` | 见 13 文档 §4 | | `aether:mcp-client` |
| `mcp_server_status` / `_tokens` / `_scopes` | | | `aether:mcp-server-read` |
| `mcp_server_start` / `_stop` / `_set_port` / `_issue_token` / `_revoke_token` / `_set_scopes` | | | `aether:mcp-server-control` |

- 不提供"显示明文密钥""导出凭据""执行任意工具""任意 SQL/文件"命令。
- 每个命令统一包装：参数上限检查 → 必要时 `spawn_blocking` → 错误序列化 → 失败记 `aether.command.failed`。

## 6. 生命周期

- `RunEvent::Exit`（`ExitRequested` 可被宿主阻止，不在那里收尾）：停止接受新运行（`chat_run` 返回 `cancelled`）→ 取消全部活动运行 → 最多等待 3 秒让它们写完终态 → 停止 MCP Server → `logs.flush()`。
- 窗口销毁：取消该窗口发起的运行（运行登记时记录 `window label`）。
- 后台任务（MCP 工具缓存刷新、探测）都持有 `CancellationToken`，退出时统一取消；不留未管理的任务。

## 7. 陷阱

1. `chat_run` 必须在启动运行**之前**完成所有校验并返回错误；启动后的任何失败只走 `end` 事件，避免同一错误报两次。
2. Channel 发送失败是取消信号，不是可忽略的错误。
3. 审批等待期间取消运行：`Approver::wait` 必须同时监听 cancel，否则运行会卡到超时。
4. `KitHost` 方法里不要长时间阻塞（如同步网络请求）：它们占用 blocking 线程池。
